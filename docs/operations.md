## 先确定故障发生在哪一段

| 现象 | 先查什么 | 如何缩小范围 |
| --- | --- | --- |
| 所有人都打不开中台 | 从受影响网络检查域名解析、证书和入口，再查服务 Pod 是否就绪 | 对照后台、Demo 和业务入口的结果，定位入口故障或业务集成故障 |
| 能进 Demo，业务页打不开 | 查看业务后端的创建结果、中台到两个业务回调的连通性、应用与签名有效期 | 按同一时间和 `fileId` 串起业务日志与中台日志，核对回调识别出的用户 |
| 文件能打开，但用户只能读 | 对照业务权限和文件元信息回调中的 `readable`、`editable` | 用同一文件切换经办人和只读账号，逐个比对实际返回权限 |
| 只有原件预览失败 | 核对文件回调的 `type`、`ext` 和 `downloadUrl` | 从中台网络确认能获取原件，再用同格式的已知正常样本比较 |
| 编辑后列表时间没更新 | 重新打开同一文件，核对正文。随后查业务端是否收到、校验并处理更新事件 | 分别记录正文保存结果与业务事件处理结果。[保存与更新机制](https://support.shimo.net/apidoc/docs-site/6000018/doc-338253) |

先核对当前集群和命名空间，再定位异常 Pod 的事件及容器日志。把下列变量替换成现场值。发生重启时，可以为 `logs` 增加 `--previous` 查看上一次容器实例的日志。

```sh
kubectl config current-context
kubectl -n "$NAMESPACE" get pods -o wide
kubectl -n "$NAMESPACE" describe pod "$POD"
kubectl -n "$NAMESPACE" logs "$POD" -c "$CONTAINER" --since=30m
```

记录版本、故障时间及其时区、影响范围、脱敏后的文件标识和首个相关错误。分享日志前移除用户信息、下载凭证、签名、Token 以及带鉴权参数的完整 URL。[服务日志](https://support.shimo.net/apidoc/docs-site/6000017/338373m0) · [监控指标参考](https://support.shimo.net/apidoc/docs-site/6000017/338875m0)

## 备份与恢复

- **确定范围。** 把 MySQL、MongoDB、Redis、对象存储以及安装配置和环境参数列入同一恢复计划。业务方另行备份自己维护的文件映射、权限和原件。先约定可接受的数据损失时间和恢复耗时，再配置备份频率、保留周期和异地副本。
- **检查备份。** 内置数据库可按版本手册核对定时任务，外部数据库由其维护方执行。定期核对最近成功时间、文件大小、可读性和副本位置。对象存储需单独备份，确认附件与数据库恢复点能够配套。
- **演练恢复。** 选定恢复点，在隔离环境恢复数据库、对象和配置。核对一份已有协同文档、一份带附件的文件以及不同用户的权限，记录实际恢复耗时。生产恢复前确认目标集群、命名空间、停写窗口和覆盖范围，并为当前数据补做备份。[数据备份机制及恢复步骤](https://support.shimo.net/apidoc/docs-site/6000017/338341m0)

## 升级与回退

1. 记录当前版本、目标版本和授权范围，在同类验证环境使用对应升级包。升级前保存数据库、对象和配置备份，记录恢复点。
2. 在管理后台的系统升级页面上传升级包，预览资源和配置差异，特别核对删除项和需要重启的服务。确认维护窗口后应用更新，保留执行日志。
3. 检查服务恢复就绪，再复测旧文件打开、双人编辑、保存后重开、只读权限，以及已接入的导入导出场景。记录任务结果和实际版本。
4. 回归失败时，保留失败日志，按升级历史中的升级前快照评估版本回退。如果还要恢复业务数据，按已演练的备份恢复流程选择恢复点，核对升级以来的新增写入。[系统升级与版本回滚](https://support.shimo.net/apidoc/docs-site/6000017/338375m0)
